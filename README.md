# 萬年曆 + 奇門遁甲（拆補法）

個人用的萬年曆／時家奇門遁甲排盤小工具，純前端、無建置流程，直接開啟 `.html` 即可使用。

## 檔案結構

```
index.html          萬年曆（農曆/節氣/宜忌），獨立頁面，不依賴下面任何 qimen-*.js
qimen.html          奇門遁甲排盤頁面（HTML 結構 + CSS，邏輯已拆到 4 個外部檔案）
qimen-engine.js     純排盤引擎(拆補法)，無 DOM 依賴，qimenChaibu() 是主入口
qimen-lexicon.js    取象詞典 LEX_DATA + 起局儀軌 RITUAL_DATA，純資料
qimen-rules.js      六害檢測/化解、主流格局判斷、財富七要/事業七要、五個所求的簡明定位讀法、
                    桃花生肖位——全是純函式/純資料，不碰 DOM
qimen-ui.js         唯一會讀寫 DOM 的一層：取象彈窗、起局儀式/歷史記錄面板、renderPan 主渲染
tests/regression.test.js   排盤引擎回歸測試(對照真實案例的快照)
RULE_AUDIT.md       逐條規則的「規則-實現-來源-適用範圍-爭議程度」審計表
```

四個 `qimen-*.js` 用傳統 `<script src>`（非 ES modules）依序載入，共用全域作用域——刻意不用
ES modules，因為本機用 `file://` 開啟時，瀏覽器的模組 CORS 限制會讓 `type="module"` 直接失效。

## 開發

```bash
npm install        # 只需裝一次 (lunar-javascript)
npm test           # 跑排盤引擎回歸測試
```

改動 `qimen-*.js` 任何一個檔案後，**先跑 `npm test`**，確保沒有把已驗證正確的結果改壞。
`qimen-engine.js`(排盤引擎) 跟 `qimen-rules.js`(六害/格局/三詐五假/簡明定位讀法/生肖桃花位)
都有回歸測試；`qimen-ui.js` 因為會直接操作 DOM，目前只能靠人工用 Playwright 手動驗證，還沒有
留在倉庫裡的自動化測試。

若要在瀏覽器裡本機驗證（CDN 在部分沙箱環境連不上）：起一個本機伺服器（如
`python3 -m http.server`），再攔截 `lunar-javascript`/`opencc-js` 這兩個 CDN 請求，改成餵
`node_modules/lunar-javascript/lunar.js` 的內容／回傳空字串即可，不需要真的連上 CDN。

## 功能與資料來源分級

奇門遁甲流派眾多，這個專案用兩個**互相獨立**的維度分級，不混在一起講——「來源可信度」回答的是
「這條規則的實作，我們查證/測試到什麼程度」，「爭議程度」回答的是「不同門派/老師之間，這條
規則本身有沒有共識」。兩者不是同一件事：同一條規則可能查證得非常仔細，卻仍然只是單一門派/
老師的特定說法(荀爽老師六害體系正是如此，本專案刻意不宣稱它是跨門派共識)；也可能是跨門派高
共識的內容，但實作上還在推導階段，沒有窮舉驗證過。之前把兩者混成一條線性分級，容易讓人誤以為
「查證得最仔細的」就等於「最普遍適用/最沒有爭議的」，兩件事拆開才不會混淆。

這兩軸其實還漏了第三個問題，用戶朋友(ChatGPT)2026-09-06 反饋時明確點出來過：「來源可信度」
跟「爭議程度」回答的都是**程式碼/規則有沒有忠實對應到某個來源**，不管答案是什麼，都無法回答
**這些解釋、化解方法是不是真的有現實預測/因果效力**——這第三個問題本質上不是程式碼能查證的
東西，本專案從一開始的定位就是老實呈現「這位老師/這些資料是怎麼講的」，不宣稱、也不試圖證明
命理判斷本身的現實有效性(這也是為什麼刻意不做「求健康」——不想讓工具被當成診斷依據)。下面
「逐字驗證」「案例驗證」這類字眼，指的都是「實作忠實對應原始資料、排盤結果可重現」，不是
「這個判斷內容被驗證為真」，兩者不要混為一談。

**來源可信度**（這條規則的實作，查證/測試到什麼程度）：

- **逐字轉錄自荀爽老師視頻，並用真實案例驗證過排盤結果可重現**：拆補法排盤引擎本身、
  六害(刑墓庚虎迫空)判斷、灭象布阵化解、財富七要／事業七要——這裡的「案例驗證」指的是
  「輸入同一組真實案例的生辰，程式排出的盤面結構(天盤/地盤/門/星/神)跟老師案例一致」，
  是排盤引擎本身的正確性驗證，不是這些判斷內容對現實有沒有預測/因果效力的驗證(後者不是
  程式碼能證明的事，見上方說明)
- **跨多個獨立命理資料源交叉核對一致，非單一教材獨有**：十天干/十二地支/八門/九星/八神取象詞典、
  後天八卦象義(GUA_XIANG)、24 個主流吉凶格局(青龍返首/飛鳥跌穴/白虎猖狂/朱雀投江/螣蛇夭矯/
  大格/小格/奇儀順遂/奇儀相佐/青龍逃走/星奇朱雀/日奇入地網/陰害陽門/日奇入墓/日奇被刑/
  日奇入天羅/火悖入刑/青龍轉光/青龍耀明/日月相會/玉女刑殺/太白逢星/人遁吉格/值符飛宮)、
  三詐五假、求權威/表現/情感/突破/桃花的
  簡明定位讀法、十二長生地利判斷、
  天盤地盤生克主客判斷、九星按月令旺相休囚死的天時判斷、門宮關係迫制和義的人和判斷、
  星／門的伏吟反吟判斷、年/月/日/時支分開起的驛馬判斷、天盤乙／庚落宮生克的婚姻用神判斷
- **推導、標記 verified:false，供人工覆核**：部分行業分類延伸(INDUSTRY_TAXONOMY)、少數化解方法
  (如三奇入墓的「用冲」推導)

**爭議程度**（不同門派/老師之間，這條規則本身有沒有共識）：
- **跨門派高共識，多個獨立來源都這麼講，相對通用**：地利/主客/天時/人和/伏吟反吟/驛馬/
  婚姻用神、24 個主流吉凶格局、三詐五假——全部歸在盤面下方「解讀一・主流斷局法」
- **單一門派/老師的特定體系，不宣稱是跨門派共識，只忠實呈現這位老師怎麼講**：六害(刑墓庚虎
  迫空)判斷跟灭象布阵化解、財富七要／事業七要——全部歸在「解讀二・荀爽老師體系」，兩套體系
  的判斷永遠分開列出，措辭上絕不寫成「主流認為…荀爽老師認為…」融在一句話裡講
- **已評估但因爭議程度過高(不同來源互相矛盾)而暫時擱置，沒有收錄進任何一套體系**：人假、
  天馬/丁馬、值符伏吟/值符反吟——查證時發現說法彼此矛盾，寧可缺一項不做也不猜，詳見下方
  「已評估、暫時擱置」段落

點擊盤面上任何天干/地干/門/星/神/宮位，會彈出對應的取象解釋，並附帶「這一宮這局命中了什麼
六害/格局」——這部分資訊全部即時算出，不是預先寫死的文字。

**這兩軸分級 2026-08-29 起同步做成 UI 上看得到的徽章**：「解讀一」「解讀二」的區塊標題、
財富七要／事業七要報告標題旁，各自掛著兩個小標籤(交叉核對/逐字驗證、跨門派共識/單一體系)，
不用回來看 README 也知道這個判斷來源可信度、爭議程度各自落在哪一格。掛在區塊標題(而不是
每張明細卡各自重複貼)，因為同一區塊裡的判斷目前分級完全一樣，逐卡重複只會洗版不會多給
資訊。簡明定位讀法(求權威/表現/情感/突破/桃花)因為內容是「跨源核對的定位方法」+「借用荀爽
灭象布阵的化解機制」的混合體，用單一徽章標記不準確，維持原本逐條「來源：...」的細粒度說明，
沒有加區塊徽章。用戶朋友(ChatGPT)反饋還建議把「解讀一」裡的地利/主客/三詐五假再細分出跟
格局/門迫/入墓/擊刑不同的子等級(理由是十二長生等未必是每個流派都拿來當核心判斷軸)，這個
沒有做——那需要另外查證每條規則在更多門派間的地位，屬於全新的分類判斷，這次只把 README
已經查證過、寫好的既有分級做成 UI 徽章，沒有藉機發明新等級。

**逐條規則的細粒度審計表**：上面兩軸是給使用者看的分類摘要(整個範疇歸進同一格)，如果想知道
「某一條具體規則(例如驛馬、三詐五假、24 個格局裡的某一個)個別的實現位置/來源/適用範圍/
爭議程度」，見 [RULE_AUDIT.md](RULE_AUDIT.md)——2026-09-06 用戶朋友(ChatGPT)第五輪反饋
建議補的逐條審計表，粒度細到每一個 `check*`/`analyze*` 函式，不跟這裡的分類摘要重複維護
同一段文字。

## 重大修正：九星/八神吉凶判斷曾經完全失效（2026-09-06）

用戶轉述朋友(ChatGPT)第四輪反饋，這次提出「代碼是否忠實實現規則／規則是否忠實來自某個
老師或傳統資料／解釋和化解方法是否具有現實效力」三層區分，並建議把整個專案的規則做成正式
稽核表。反饋裡具體指出：`luckClass()`(`qimen-rules.js`) 把天蓬列為吉、九地列為凶，跟一般
命理資料的描述方向相反，而這個函式的結果會直接影響婚姻用神的 `hasLuckySymbol` 判斷，不只是
視覺問題。

覆核這個具體指控時，發現問題比反饋描述的更嚴重：**`luckClass()` 對星、神兩類的吉凶判斷，
從功能存在以來就完全沒有生效過，不是「分類錯誤」，而是「根本沒有分類」**。原因：這個函式
判斷星/神吉凶用的陣列，寫的是「天輔」「天任」「天蓬」「值符」「太陰」這種完整兩字名稱，但
盤面(`pan.星`／`pan.神`)實際存的是單字代碼(「輔」「任」「蓬」「符」「陰」)——字串完全對不上，
`.includes(v)` 永遠不會命中，於是不管實際是哪個星、哪個神，一律回傳中性(`pill-neutral`)，
而且完全不會報錯，是純粹的靜默失效。影響範圍：

1. **九宮格下方「吉凶速覽」卡片**：星、神欄位的顏色徽章，從這個功能上線以來就一直只顯示
   中性色，從沒有真的按實際星/神顯示過紅/綠色——這是每一次起局都看得到的核心畫面，不是
   邊緣功能。
2. **婚姻用神 `hasLuckySymbol` 判斷**：`checkYiGengMarriage()` 原本設計是「乙、庚任一方
   逢吉門/吉星/吉神都算加分」，但因為這個 bug，星、神從來沒有真正參與過判斷，`hasLuckySymbol`
   實際上只看得到門的吉凶——這個功能上線時寫的回歸測試剛好只測到門觸發的案例(用
   `{乾:'開', 離:''}` 這種只設定門的資料)，沒有測到星/神觸發的案例，所以沒有在當時被抓到。

門的判斷本身格式沒有問題(盤面門值本來就是單字，跟陣列裡的單字對得上)，這部分維持不動。
星/神的判斷改成直接查 `LEX_DATA.stars`／`LEX_DATA.gods` 的 `luck` 欄位——這張表在
`qimen-lexicon.js` 開頭就寫明來源是「多個獨立命理資料來源交叉比對整理」，鍵值本來就是跟
盤面一致的單字代碼，不需要另外維護一份格式不同、沒有來源說明、內容還互相矛盾的清單(原本
`luckClass()` 把天蓬列吉、天英列凶、九地列凶，但 `LEX_DATA` 分別記錄成凶／中平／吉，兩邊
互相矛盾；`LEX_DATA` 有文件說明來源，`luckClass()` 完全沒有註解說明依據，以 `LEX_DATA` 為準)。
`LEX_DATA` 裡「次吉」「中平」這兩檔暫時都歸類為中性，不強行二分成純吉或純凶，跟原本沒被
任何一個陣列收錄的門(如杜/景)是同一種處理方式。

修正後補了 30 條回歸測試(`luckClass()` 逐一測過全部門/星/神代碼，`checkYiGengMarriage`
補星觸發、神觸發、天蓬單獨出現不算吉三個案例)，用 Playwright 截圖確認「吉凶速覽」卡片現在
星、神欄位確實出現紅/綠色，不再全部是中性灰底，0 console error。`npm test` 174 條全部通過。

用戶朋友這次的反饋方向本身很值得認真對待：分清楚「程式碼有沒有忠實實現規則」「規則有沒有
忠實反映某個老師/傳統資料」「這些解釋和化解方法有沒有現實效力」三件事，第三件事本來就是
本專案從一開始就講清楚不宣稱、不做健康診斷的立場，前兩件事才是程式碼層面真正能查證的範圍。
反饋建議把全部規則整理成「規則—實現—來源—適用範圍—爭議程度」的正式稽核表、逐項查證，
這個方向認同，但工程量很大，這次先處理反饋裡指出、且經查證確認影響範圍比反饋描述更嚴重的
這一項，正式稽核表留待後續規劃。

**同一輪反饋另外三個小修正**：
1. **「正西或正北」的來源釐清**：反饋質疑這個「無腦法」安全方位到底是老師原話還是專案自行
   推導，查證後發現問題出在程式碼裡剛好有兩個相鄰但性質不同的常數容易被看混——`WUNAOFA_DEST`
   (實際被使用、來源是荀爽老師「無腦法」視頻畫面逐字轉錄)跟 `SAFE_BUZHEN_GONG`(專案自行
   推導、但整個專案沒有任何地方真的用到它，是早期探索階段留下的死代碼)。已刪除
   `SAFE_BUZHEN_GONG`，只留下實際使用、且已經清楚寫明來源的 `WUNAOFA_DEST`，避免兩種不同
   性質的依據混在一起看。
2. **「真實案例驗證」措辞精確化**：README「來源可信度」段落原本寫「並有真實案例驗證」，容易
   被誤讀成「這些命理判斷內容被驗證為真」，但實際驗證的是「輸入同一組真實案例的生辰，程式
   排出的盤面結構(天盤/地盤/門/星/神)跟老師案例一致」，是排盤引擎正確性的驗證，跟判斷內容
   本身有沒有現實效力是兩件事。已改寫措辭，並在兩軸分級說明的開頭加一段，明講「來源可信度」
   跟「爭議程度」都只回答程式碼/規則有沒有忠實對應來源，不回答、也無法回答判斷內容的現實
   預測/因果效力(這第三個問題不是程式碼能查證的東西)。
3. **格局/六害描述的斷言語氣**：24 個主流吉凶格局跟荀爽老師六害體系裡，部分描述沿用傳統
   典籍/教材的原始措辭，字眼較重(如「百事皆凶」「車禍意外」「炎症/發炎類疾病」)，讀起來容易
   像是工具在斷定使用者現實中一定會發生這些事。沒有更動任何一條已查證的原始文字內容(改寫
   原文有走樣風險)，而是在「解讀一」格局卡跟師傅總結卡各加一段共用的提醒文字，講清楚這些是
   傳統文字上的比喻性/警示性描述，不是本工具對現實的斷定，尤其涉及健康/意外的字眼不能當醫療
   或安全判斷依據——跟本專案一開始就明確不做「求健康」的立場一致。

三項都是純文字/文件層級的修正，`npm test` 174 條照常通過，Playwright 確認兩張卡片都正確
顯示新增的提醒文字，0 console error。

**同一輪反饋第四項：化解步驟可信度粒度**(這項當初評估影響範圍較大、單獨排開)：
`formatCureSteps()`(`qimen-rules.js`) 把化解步驟拆成「字/物/意/行」四個維度呈現，但原本
只有整條步驟一個 `verified` 狀態。查證後確認反饋指出的落差是真的：「意」「行」兩維固定
來自 `WUXING_YI_XING` 這張表(該表本身已經明確標註「非逐字視頻原文，為五行常理推導」)，
「字」「物」兩維則是複述上層 cure 已經選定的天干、加上 LEX_DATA 的顏色材質(跟上層 cure
本身的可信度是同一件事)。四維混在一起共用一個 verified，會讓「意/行」這種明確標記過的
推導內容看起來跟「用合天干五合(逐字視頻原文)」一樣可信。已改成 `formatCureSteps()` 給

## 師傅總結（白話總結卡，2026-08-29 新增）

用戶原話：「其实你看所有主流的这类app，都是起局容易，出命盘容易，每一个术语也有解释，但是

正下方會出現一張「師傅總結」卡，依「這局最該注意的程度」排出最多 3 個宮，逐宮把兩套體系的

   具體擺放指令，改用 `MINGJU_CURE_NOTE` 說明原因，並建議針對具體的事另外起事局來問。

## 預註冊式驗證日誌（2026-08-29 新增）

這個功能的背景：用戶轉述朋友(ChatGPT)對這個專案的「規則審計」建議時，提過「拿過去人生
大事回測」來驗證準確率，討論後認為這個方法論本身有問題——事後回頭找理由解釋一件已經知道
結果的事，能力遠高於事前真的預測對，這是典型的確認偏誤陷阱，不足以當作驗證。真正站得住腳
的作法是：起局當下先留下判斷，不看結果，等時間到了再回頭對照，而不是先知道結果才回去湊
一個「準」的解讀。同時這個方向也明確不強求——不會為了湊驗證樣本刻意多起局，只在用戶原本
就會自然起局的時候，順手把這個記錄留下來。

實作上接在既有的「起局歷史記錄」(`localStorage`，只存本機瀏覽器)基礎上：
- 每次起局時，`renderPan()` 把當下算出的「師傅總結」熱點宮判斷(荀爽老師體系+主流斷局法
  各自的完整文字、命中號令/背景標記)原封不動存成 `prediction` 快照，寫進歷史記錄裡。
- 歷史記錄面板裡，這份快照用唯讀的 `<details>` 摺疊區塊顯示，標題明講「預註冊，鎖定不可改」，
  跟下面本來就有的「事後回看」可編輯文字框位置上下並排——事後回看時，看到的是「起局那一刻
  真的判斷了什麼」，不是憑印象事後重構，才有真正的校對意義。
- 只是資料快照跟顯示邏輯，完全不影響任何判斷函式，`npm test` 136 條全部照常通過。舊有
  (這個功能上線前)的歷史記錄沒有 `prediction` 欄位，面板會顯示「此筆記錄建立於功能上線前」
  的說明文字，不會顯示空白或報錯。
- 開發時順便發現一個既有的 CSS 小問題：`.h-row`(每筆歷史記錄的外層容器)原本是
  `display:flex`，設計上是讓「本行資訊」跟「事後回看」兩欄並排半版寬；這次新增的預註冊
  快照變成第三個要並排的區塊，繼續平分寬度會把每一欄都擠得太窄(事後回看的輸入框一度被壓縮
  到只剩 80 幾像素寬，幾乎沒法打字)。已經改成直向堆疊(`display:block`)，順便讓事後回看
  欄位拿到整行寬度，比原本的半版寬更好用，不是退步。

**歷史記錄三個問題修正(Codex code review，2026-09-03)**：用戶請 Codex(另一個 AI 工具)對
這個專案做了一輪獨立 code review，抓到三個「起局歷史記錄」功能既有的實際問題，Claude 逐一
讀原始碼確認屬實後修正：

1. **重新載入歷史記錄無法準確重現原本的盤**(P1，影響正確性)：`reloadHistoryRecord()`
   原本只還原日期/時間/所求/生年/局類型，沒有還原**經度、行業、月令比較對象**這三個欄位，
   重新載入時會直接沿用畫面上目前的值。經度會影響真太陽時校正，甚至能讓時柱(有時連日柱)
   整個變掉(用不同經度重算同一組年月日時，實測日柱/時柱確實會不一樣)，等於同一筆歷史記錄
   兩次點開可能排出不同的盤，「回看」的前提就不成立了。修法：`pushHistoryRecord` 補存
   `longitudeInput`／`industry`／`targetWuxing` 三個欄位，`reloadHistoryRecord` 對應
   還原(行業是「大行業／小行業」兩層下拉，需要先設回大行業、觸發小行業選項重新產生，才能
   設回小行業的值，寫成獨立的 `restoreIndustrySelect()`)；功能上線前的舊記錄沒有這三個
   欄位時，一律還原成空值(不校正/不選行業/不比較月令)，誠實反映「這筆舊記錄本來就沒存這項
   資訊」。用 Playwright 實測驗證：同一組年月日時分，經度 87.62 跟 -118.24 排出的日柱/
   時柱確實不同，證明經度真的會影響盤面；刻意把畫面上的經度改成別的值後點開歷史記錄，
   排出的盤仍然跟原本存檔時一致。
2. **檢視歷史記錄會多產生一筆一模一樣的新記錄**(P2)：`reloadHistoryRecord()` 呼叫
   `calc()`，而 `calc()`／`renderPan()` 原本無條件呼叫 `pushHistoryRecord()`，等於每點開
   一筆舊記錄就多一筆重複記錄，長期會把清單洗版、擠掉真正的舊資料。修法：`calc()`／
   `renderPan()` 加一個 `skipHistory` 參數，`reloadHistoryRecord()` 呼叫時傳 `true`，
   只有真正手動按「起局」按鈕才會寫入新記錄。Playwright 實測：點開歷史記錄前後，記錄筆數
   不變。
3. **匯入備份檔案存在儲存型 HTML 注入風險**(P2，安全性)：`importHistoryJson()` 原本只
   檢查匯入內容「是不是陣列」，之後 `dateStr`／`needKey`／`prediction` 文字、`id` 等欄位
   會直接被拼進 `innerHTML`／`onclick` 屬性；被竄改過或來路不明的備份檔案可以藉此在瀏覽器
   裡跑任意腳本(例如 `id` 不是乾淨數字就能跳出 `onclick="reloadHistoryRecord(...)"` 屬性
   插入任意程式碼)。修法是雙層防護：(1) 新增 `sanitizeHistoryRecord()`，匯入時嚴格校驗
   每筆記錄的欄位型別，`id` 只接受有限數字，其餘文字欄位一律轉成安全的字串(不是字串就丟
   空字串)，形狀不對的記錄整筆捨棄而不是整包收下；(2) `renderHistoryPanel()`／
   `renderPredictionSnapshot()` 對所有原本沒轉義的文字欄位補上既有的 `escHtml()`，
   `id` 嵌入 `onclick` 前也另外做一次有限數字檢查，兩層防護互相獨立，不因為某一層漏網
   就整個失守。Playwright 用兩份構造過的惡意備份檔案實測：一份帶非數字 `id`(整筆被
   `sanitizeHistoryRecord` 丟棄)、一份帶合法數字 `id`但每個文字欄位都夾帶
   `<img onerror=...>`／`<script>`／屬性逃逸字串(全部欄位在畫面上都被 `escHtml` 正確
   轉成逸出文字，沒有真的產生標籤)，兩種情況下注入的探測程式碼都沒有被執行，0 console
   error。

三項修正都不影響任何判斷邏輯(格局/六害/財富七要等)，`npm test` 144 條照常通過，純粹是
歷史記錄這個輔助功能本身的正確性跟安全性補強。

## 進行中的擴充計畫：主流斷局法四要素(原規劃五要素，見下方 2026-09-06 修正)
