# 萬年曆 + 奇門遁甲（拆補法）

個人用的萬年曆／時家奇門遁甲排盤小工具，純前端、無建置流程，直接開啟 `.html` 即可使用。

## 檔案結構

```
index.html          萬年曆（農曆/節氣/宜忌），獨立頁面，不依賴下面任何 qimen-*.js
qimen.html          奇門遁甲排盤頁面（HTML 結構 + CSS，邏輯已拆到 4 個外部檔案）
qimen-engine.js     純排盤引擎(拆補法)，無 DOM 依賴，qimenChaibu() 是主入口
qimen-lexicon.js    取象詞典 LEX_DATA + 起局儀軌 RITUAL_DATA，純資料
qimen-rules.js      六害檢測/化解、主流格局判斷、財富七要/事業七要、五個所求的簡明定位讀法、
                    桃花生肖位——全是純函式/純資料，不碰 DOM
qimen-ui.js         唯一會讀寫 DOM 的一層：取象彈窗、起局儀式/歷史記錄面板、renderPan 主渲染
tests/regression.test.js   排盤引擎回歸測試(對照真實案例的快照)
```

四個 `qimen-*.js` 用傳統 `<script src>`（非 ES modules）依序載入，共用全域作用域——刻意不用
ES modules，因為本機用 `file://` 開啟時，瀏覽器的模組 CORS 限制會讓 `type="module"` 直接失效。

## 開發

```bash
npm install        # 只需裝一次 (lunar-javascript)
npm test           # 跑排盤引擎回歸測試
```

改動 `qimen-*.js` 任何一個檔案後，**先跑 `npm test`**，確保沒有把已驗證正確的結果改壞。
`qimen-engine.js`(排盤引擎) 跟 `qimen-rules.js`(六害/格局/三詐五假/簡明定位讀法/生肖桃花位)
都有回歸測試；`qimen-ui.js` 因為會直接操作 DOM，目前只能靠人工用 Playwright 手動驗證，還沒有
留在倉庫裡的自動化測試。

若要在瀏覽器裡本機驗證（CDN 在部分沙箱環境連不上）：起一個本機伺服器（如
`python3 -m http.server`），再攔截 `lunar-javascript`/`opencc-js` 這兩個 CDN 請求，改成餵
`node_modules/lunar-javascript/lunar.js` 的內容／回傳空字串即可，不需要真的連上 CDN。

## 功能與資料來源分級

奇門遁甲流派眾多，這個專案用兩個**互相獨立**的維度分級，不混在一起講——「來源可信度」回答的是
「這條規則的實作，我們查證/測試到什麼程度」，「爭議程度」回答的是「不同門派/老師之間，這條
規則本身有沒有共識」。兩者不是同一件事：同一條規則可能查證得非常仔細，卻仍然只是單一門派/
老師的特定說法(荀爽老師六害體系正是如此，本專案刻意不宣稱它是跨門派共識)；也可能是跨門派高
共識的內容，但實作上還在推導階段，沒有窮舉驗證過。之前把兩者混成一條線性分級，容易讓人誤以為
「查證得最仔細的」就等於「最普遍適用/最沒有爭議的」，兩件事拆開才不會混淆。

**來源可信度**（這條規則的實作，查證/測試到什麼程度）：

- **逐字轉錄自荀爽老師視頻，並有真實案例驗證**：拆補法排盤引擎本身、六害(刑墓庚虎迫空)判斷、
  灭象布阵化解、財富七要／事業七要
- **跨多個獨立命理資料源交叉核對一致，非單一教材獨有**：十天干/十二地支/八門/九星/八神取象詞典、
  後天八卦象義(GUA_XIANG)、11 個主流吉凶格局(青龍返首/飛鳥跌穴/白虎猖狂/朱雀投江/螣蛇夭矯/
  大格/小格/奇儀順遂/奇儀相佐/青龍逃走/星奇朱雀)、三詐五假、求權威/表現/情感/突破/桃花的
  簡明定位讀法、十二長生地利判斷、
  天盤地盤生克主客判斷、九星按月令旺相休囚死的天時判斷、門宮關係迫制和義的人和判斷、
  星／門的伏吟反吟判斷、年/月/日/時支分開起的驛馬判斷
- **推導、標記 verified:false，供人工覆核**：部分行業分類延伸(INDUSTRY_TAXONOMY)、少數化解方法
  (如三奇入墓的「用冲」推導)

**爭議程度**（不同門派/老師之間，這條規則本身有沒有共識）：
- **跨門派高共識，多個獨立來源都這麼講，相對通用**：地利/主客/天時/人和/伏吟反吟/驛馬、
  11 個主流吉凶格局、三詐五假——全部歸在盤面下方「解讀一・主流斷局法」
- **單一門派/老師的特定體系，不宣稱是跨門派共識，只忠實呈現這位老師怎麼講**：六害(刑墓庚虎
  迫空)判斷跟灭象布阵化解——全部歸在「解讀二・荀爽老師體系」，兩套體系的判斷永遠分開列出，
  措辭上絕不寫成「主流認為…荀爽老師認為…」融在一句話裡講
- **已評估但因爭議程度過高(不同來源互相矛盾)而暫時擱置，沒有收錄進任何一套體系**：人假、
  天馬/丁馬、值符伏吟/值符反吟——查證時發現說法彼此矛盾，寧可缺一項不做也不猜，詳見下方
  「已評估、暫時擱置」段落

點擊盤面上任何天干/地干/門/星/神/宮位，會彈出對應的取象解釋，並附帶「這一宮這局命中了什麼
六害/格局」——這部分資訊全部即時算出，不是預先寫死的文字。

## 師傅總結（白話總結卡，2026-08-29 新增）

用戶原話：「其实你看所有主流的这类app，都是起局容易，出命盘容易，每一个术语也有解释，但是
没有一个app有那种分析、解释，把该命盘像一个遁甲师傅一样，以人的口味告诉你里面的内容，需要
注意的地方，每一个意思是什么，整个盘最需要注意的地方是什么，凶吉代表什么，如何避免，如何
破解，如何面对」——这正是`buildMasterSummary()`(`qimen-rules.js`)要補的空白：起局後盤面
正下方會出現一張「師傅總結」卡，依「這局最該注意的程度」排出最多 3 個宮，逐宮把兩套體系的
判斷**分開列出**（絕不融在一起講，這是用戶明確要求的紅線），荀爽老師體系的部分附完整的
灭象/布阵化解步驟（灭象動作 + 字/物/意/行四維度 + 方位），主流斷局法的部分誠實標註「目前
沒有對應的化解方法」。

技術上刻意不做自由生成的文字——每一句敘述都是「固定模板套用某個既有 check* 函式的真實輸出」
組出來的，不是即時生成的自然語言，這樣才能保證跟其他規則層一樣可控可測試，不會出現語氣過度
武斷或前後矛盾的問題。「命中號令」的定義沿用既有的號令機制(日干/時干/值符/所求對應天干)，
排序權重是「命中號令的信號」> 「背景信號」，兩套體系在同一宮方向是否一致(consistent/mixed)
也會如實標註，不強行調和成單一結論。

**上線當天用戶實測就抓到兩個準確率問題，都已修正**：
1. 灭象布阵給的「方位」(如「正西或正北」)，指的是**布阵物品/文字要擺放的位置**(家裡或
   辦公室的某個方向角落)，跟「本人現實中該不該去這個方向」完全是兩件事——原本的文案只寫
   「方位：正西或正北」，沒有講清楚是哪一種，容易被誤讀成後者。已改成明確講「把物品放在
   家裡的...角落」並註明跟現實去向無關。
2. 更關鍵的問題：**灭象布阵這套具體到「擺什麼物品、放哪個方位」的操作方法，是荀爽老師針對
   「事局」(問一件具體的事)設計的**，命局代表一個人天生的整體結構，不是在問一件具體的事，
   硬套這套操作指令會文不對題，讓人覺得「不准」。已修正為：`buildXunlaoItems()`/
   `buildMasterSummary()` 現在會依 `juType`(事局/命局)區分——事局模式維持完整灭象布阵步驟；
   命局模式下「命中了什麼」照樣顯示(這是命局固有的結構特徵，判斷本身沒問題)，但不再給出
   具體擺放指令，改用 `MINGJU_CURE_NOTE` 說明原因，並建議針對具體的事另外起事局來問。

**上線後做的一輪 UI 檢視(手機寬度截圖實測)，修正兩個問題**：
1. 命局模式下，`MINGJU_CURE_NOTE` 原本每一條命中的六害都各自貼一遍，同一張卡片裡重複兩三次
   一模一樣的長句，顯得機械囉唆——這正是用戶擔心的「機器感」在新地方復現。已改成整張卡片
   (每個宮)只在最後統一講一次，不逐條重複。
2. 新增「回頂部」小圓鈕(`#backToTopBtn`，`qimen.html`)：命局+財富七要這類完整報告在手機
   寬度下要滑 10 幾屏，原本完全沒有導航手段。平常不佔位置，滑過 500px 後才淡入顯示；同時
   把常駐的「萬年曆」按鈕透明度調低、尺寸縮小一點，減少對卡片內容右下角的遮擋。

**師傅總結卡跟下面「解讀一」完整明細卡之間的重複內容**：用戶要求刪減，跟用戶確認過方向是
「精簡下方完整明細卡，師傅總結卡保持現狀」——因為師傅總結是主要閱讀入口，完整明細卡是給
想深挖的人看的參考資料，不需要把師傅總結已經講過的完整解釋再貼一遍。做法：`renderPan()`
建立一個 `hotspotGongs` 集合(師傅總結挑出來的最多 3 個宮)，格局/三詐五假/地利/主客/天時/
人和這 6 張明細卡，遇到屬於 `hotspotGongs` 的宮時，改成精簡一行(宮位+關鍵狀態+命中號令
徽章+「同上方師傅總結，此處從簡」小字提示)，不屬於熱點宮的資料維持完整解釋不變。伏吟反吟
卡因為是整局現象、不進入師傅總結的逐宮彙整，沒有重複問題，不用動；解讀二的六害「本局解讀」
敘事卡結構較複雜、風險較高，這次沒有一併精簡，只處理了「解讀一」這 6 張結構單純的卡片。

**輸入面板調整(用戶截圖回饋，2026-08-29)**：
1. 經度改成先選城市快速帶入——大多數人不知道自己所在地的精確經度，直接要求手動輸入不現實。
   新增「地點」下拉(`#iCityPreset`，`qimen-ui.js` 的 `CITY_LONGITUDE`)，涵蓋中國大陸/港澳台/
   海外常見約 45 個城市，選了自動帶入經度；手動輸入欄位保留，供需要更精確地點的情況使用，
   兩者不衝突。
2. 「所求」下拉選項原本把驗證狀態說明(如「完整報告」「推導未驗證」)直接寫進選項文字，長度
   落差太大導致選單看起來一長一短很不協調；改成選項只留核心名稱，驗證狀態說明移到選單下方
   統一一行講清楚。
3. 「局類型」欄位移到輸入面板最上方——命局還是事局要先決定，後面「所求」「經度」的填法都
   跟著這個選擇走，原本放在最後面容易讓人先填完其他欄位才想到局類型沒選對。

**「命中號令」徽章視覺權重 + 背景條目預設折疊(2026-08-29)**：先前 UI 檢視列出但沒動的項目，
這次補上。問題：地利/主客/天時/人和/驛馬這幾張明細卡，一個宮位常常大部分條目都是「背景」
(沒有直接命中你)，只有一兩條是「命中號令」，但兩種徽章原本只靠顏色深淺區分(`hl-hit` 淺紅底/
`hl-bg` 淺灰底，字級、粗細都一樣)，全部攤開平鋪反而讓真正要緊的訊號被淹沒在一堆背景資訊裡。
做法：(1) `hl-hit` 改成深紅實心底+白字+陰影，`hl-bg` 維持灰底但加深透明度，兩者視覺權重明確
拉開，不用逐字讀內容就能一眼分辨；(2) 新增 `renderWithBgCollapse()`(`qimen-ui.js`)，把每張
明細卡裡「既非師傅總結熱點宮、也沒命中號令」的純背景條目收進 `<details>` 預設折疊，只留一行
「▸ 展開其餘 N 條背景資訊」，命中號令跟熱點宮精簡列都維持直接展開不受影響。純 CSS/DOM 呈現
調整，不改變任何判斷邏輯，`npm test` 125 條全部照舊通過；Playwright 對事局/命局 × 5 個日期 ×
4 個時刻 × 全部所求選項共 360 組合掃描，0 console error，並截圖確認折疊/展開兩種狀態都正常。

開發時發現一個值得記錄的插曲：用真實命局(1988-02-23 20:45)手動寫第一版總結時，把「值符所在
的宮」跟「值符這個天干本身被打擊」混為一談了(誤以為值符癸入墓，實際入墓的是同宮的另一個
天干丁)——自動化引擎因為嚴格按「isHit=該天干是否為護體天干」判斷，正確地把這個宮的入墓/
格局標成「背景」而非「命中號令」，比人工口頭分析更精確。這提醒了一件事：讓判斷邏輯完全
數據驅動、可測試，比憑印象講故事更可靠。

## 進行中的擴充計畫：主流斷局法五要素

用戶的方向：不是拿主流內容取代荀爽老師體系，而是同一個判斷點，**兩套結果並排展示**，讓使用者
自己比較、自行選擇要看哪一套。主流斷局法公認的框架是**天時、地利、人和、神助、主客**五個維度，
目前只有「人和」的一部分(門迫)跟這套框架沾邊，其餘大多要另外補基礎設施。進度：

- [x] **地利（十二長生）** — 2026-08-29 完成。十天干起長生的地支+陰陽干順逆行方向，三個獨立
  資料源交叉核對一致。得地利(長生/臨官/帝旺)、失地利(死/墓/絕)兩種狀態，四角宮(艮/巽/坤/乾)
  各兩個地支分開列，不強行合併成一個結論。天盤/地盤都各自獨立算(代表現在/未來 vs 過去)。渲染
  上沿用「號令」保護天干的機制，區分「命中號令」跟「背景」。獨立一張卡片，跟荀爽老師體系分開。
- [x] **主客（天盤干/地盤干生克關係）** — 2026-08-29 完成。天盤隨時辰轉動視為「客」，地盤
  一局內不動視為「主」；被克/被生的一方利益歸誰：天盤克地盤或地盤生天盤＝利客，地盤克天盤
  或天盤生地盤＝利主，五行相同(比和)則主客同心不分勝負。掃描全部 8 個外宮(中宮不計)，沿用
  「號令」機制標示命中號令 vs 背景，獨立卡片跟地利、荀爽老師體系都分開。
- [x] **天時（九星按月令旺相休囚死）** — 2026-08-29 完成。查證時發現九星的旺相休囚廢
  跟一般八字五行旺相休囚死的判斷基準點不同(多方獨立來源解釋一致，非單一部落格說法)：八字拿
  「地上五行」跟「當令季節」比，同我者旺；奇門九星拿「星曜」跟「當令月支五行」比，我生月令
  才是旺，跟月令同五行只排第二(相)。用天蓬(水)的具體案例逐一核對過。得天時(旺/相)、失天時
  (囚/死)兩種狀態，休＝中性不列出。獨立卡片，跟六害/格局/地利/主客都分開。
- [x] **人和補全（門宮關係 迫/制/和/義）** — 2026-08-29 完成。門克宮＝迫(荀爽老師六害
  體系已經在用，這裡放進完整脈絡對照)、宮克門＝制、門生宮＝和、宮生門＝義，五行相同為比和；
  迫/制不利(原本吉的門吉不全、原本凶的門更凶)，和/義有利。查證時搜到一次語序相反的說法，
  額外用精確詞句比對 3 個獨立來源才鎖定，避免像「人假」那樣誤收矛盾說法。
- [x] **伏吟反吟（星／門）** — 2026-08-29 完成。伏吟＝星或門落在自己的洛書固定本宮(停滯
  僵化)，反吟＝落在本宮的正對沖宮(衝突反覆)。實測發現(不是憑空假設，是拿真實案例窮舉驗證出
  來的結構性事實)：因為星盤/門盤整圈一起轉動，伏吟/反吟永遠是整局同時出現(8個外宮同時命中
  同一種)，不會只有單一宮位孤立命中；荀爽老師案例本身(2024-02-28 18:39)剛好就是一個門反吟
  局。這裡不標吉凶，因為伏吟反吟的意象比較複雜(伏吟＝停滯，反吟＝變動、也可能失而復得)，
